Architecture, Integration APIs & Scaling to Telco-Grade
This build is a self-contained browser prototype. This page documents how a production/telco deployment differs.

What this prototype actually is

Everything runs client-side in this one HTML file: chunking, TF‑IDF retrieval, language/sentiment heuristics, the workflow engine, and the "database" (browser IndexedDB standing in for MySQL). LLM calls go straight from your browser to Gemini/Groq/OpenRouter/HuggingFace using a key you paste into Settings — fine for personal/demo use, not for production (keys are exposed client-side, and IndexedDB doesn't survive across devices or browsers).

Workflow module

Workflows are decision trees ({start, nodes:{...}}) generated from a natural-language prompt, but only using the operator's own knowledge base as context — the generator retrieves relevant chunks first and refuses to build anything if there isn't enough KB coverage, so it can't invent an ungrounded scenario. Nodes can be question (branches to buttons), answer (terminal), input (collects a typed value into a variable), or api_call (a real fetch() to an external API, with the response stored in a variable and interpolated into later node text via {{variable}}) — letting a workflow reach outside the chatbot into the operator's own systems (order status, ticket creation, etc.), subject to that API's CORS policy since calls run directly from the browser here. Workflows are stored as plain JSON in IndexedDB (workflows store), edited visually as a diagram or via raw JSON, and matched to incoming queries client-side via keyword/phrase (Jaccard) overlap against each workflow's trigger list — no LLM call is needed to route a query into a workflow, which is what keeps simple, repetitive questions off the RAG/LLM path entirely. In a production backend this becomes its own service: POST /v1/workflows/generate (prompt → draft JSON, still human-reviewed before publish), POST /v1/workflows / PUT /v1/workflows/{id} to publish, a server-side proxy for api_call steps (so CORS and credentials are handled off the client), and the query router calls an intent-matching step (could stay lexical, or upgrade to a small classifier/embedding lookup) before falling back to vector retrieval + LLM.

External integration API surface (for a real backend)

To let other systems (IVR, CRM, mobile apps, agent desktops) push input and receive output at scale, expose a thin REST/webhook layer in front of the RAG pipeline:

  • POST /v1/documents — ingest a file or raw text into the knowledge base; accepts chunk_size/overlap or "auto".
  • GET /v1/documents/{id}, DELETE /v1/documents/{id} — manage KB entries.
  • POST /v1/workflows/generate — prompt → draft workflow JSON for review.
  • POST /v1/workflows, PUT /v1/workflows/{id}, DELETE /v1/workflows/{id} — publish/manage workflows.
  • POST /v1/query — synchronous text query → { answer, source: workflow|cache|llm, language, sentiment, latency_ms, citations[] }.
  • POST /v1/query/stream — Server-Sent Events / WebSocket variant for token-by-token streaming (needed for natural voice/chat UX).
  • POST /v1/voice — audio in (multipart or streaming) → STT → same pipeline → TTS audio out.
  • POST /v1/webhooks/subscribe — register a callback URL to receive async answers (useful for long-running or queued requests).
  • GET /v1/reports/mis?from=&to=&status= — MIS/analytics export, paginated, CSV/JSON.
  • POST /v1/feedback — thumbs up/down or corrected answer, used to curate what gets promoted into the historic-answer cache or a workflow.

Auth: OAuth2 client-credentials or signed API keys per tenant, rate-limited per key; all endpoints versioned and behind an API gateway.

What changes to run this at telco scale

  • Database: real MySQL (or Postgres) cluster with read replicas for chat history/MIS/workflow definitions, not IndexedDB — plus a proper vector store (pgvector, Milvus, or a managed vector DB) replacing the in-browser TF‑IDF index once corpus size grows past what brute-force cosine similarity can handle in real time.
  • Caching layer: Redis (or similar) in front of MySQL for the "check history before calling the LLM" lookup, so cache hits stay sub-50ms under load.
  • LLM gateway: a backend service holds provider API keys (never the client), load-balances across providers/models, handles retries, timeouts, and fallback ordering (e.g., Groq first for latency, Gemini as fallback).
  • Async/queueing: Kafka or SQS/RabbitMQ to decouple ingestion (large document/PDF processing, embedding generation) and bursty voice traffic from the request path.
  • Compute: containerized microservices on Kubernetes with autoscaling (HPA) for the API layer, STT/TTS workers, and embedding workers sized independently.
  • Telephony/voice integration: SIP/IVR gateway or WebRTC bridge in front of the voice endpoint; dedicated STT (e.g., streaming ASR) and TTS services sized for concurrent call volumes, not browser Web Speech API. Workflows map naturally onto IVR menu trees here.
  • Multi-tenancy: tenant isolation at the DB and vector-index level (per-tenant schema or partition key) so one telco business unit's KB or workflows never leak into another's answers.
  • Observability: centralized logging, distributed tracing (OpenTelemetry), and dashboards (Prometheus/Grafana) tracking cache-hit rate, workflow-deflection rate, LLM cost per query, latency percentiles, and failure rate — this MIS page becomes a real-time ops dashboard fed by the same pipeline.
  • Reliability: multi-AZ/multi-region deployment, DB failover, circuit breakers around each LLM provider, graceful degradation to workflows/cached/FAQ answers if all providers are down — telco environments typically target 99.99%+ availability.
  • Security & compliance: encryption at rest/in transit, PII detection/redaction before data reaches a third-party LLM, audit logs, data residency controls, and role-based access (e.g., only certain roles can publish workflows) — especially important given telco regulatory obligations (e.g., call/customer data handling rules).
  • Cost governance: per-tenant/per-query budget caps, model routing by query complexity (workflow first, then cheap/fast model, escalate only if confidence is low), and the cache-first + workflow-first pattern already in this prototype — which is exactly the right instinct for controlling LLM spend at volume.
